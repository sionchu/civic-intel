- 기관증인: 87개 기관 제목 표, 직위 370행, 이름 셀 369개.

- 합계 412개 직위/요구 행. 이 수는 고유 인물 수 또는 전국 명단 수가 아니다.

  PDF 셀 좌표를 근거로 두 직위의 같은 이름 셀 키를 유지했다. 빈칸 추정으로 새 사람을 만들지 않았다.
- 기관별 인원 표기와 이름 셀 수는 87개 표 모두 일치했다. 열 제목·필드 위치·행 키의
  유일성, 입력 PDF 해시, 정규화 해시를 확인했다. 대표 공개 필드의 PDF 렌더를 열어 대조했다.
- 전체 행의 사람 검토는 미실행이다. 추가·철회·교체 문서의 전국 최신성도 확인하지 않았다.
  파일명에 있는 “최종”을 이후 변경이 없다는 뜻으로 해석하지 않는다.

## 프론트엔드·백엔드 진행안

이제 작업 단위는 **위원회 → 감사 일정·피감기관 → 기관증인/일반증인/참고인 → 인물·소속 → 근거**다.
기관증인은 기관별로, 일반증인·참고인은 원문 대상기관과 요구 일시별로 함께 준비한다.

1. **출처별 검토 계약:** 기존 계획 패킷에 증인 행을 넣지 않는다. 출석 명단 전용 필드 계약에서
   세 범주, 원문 대상기관, 소속·직위, 일시의 부재, 병합 셀, 정확한 페이지·행·원문 SHA를 보존한다.
   연구 DRAFT를 `HUMAN_REVIEWED`로 승격하려면 실제 필드별 사람 검토가 필요하다.
2. **내부 검토 인입:** 기존 SourcePolicy → Source → metadata-only SourceSnapshot →
   SourceRun/Checkpoint → FeederObservation 경로를 사용한다. 새 테이블이나 raw 저장소가
   필요한 상황은 확인되지 않았다. 같은 원문/정규화의 재실행은 무효과, 변경은 새 관측으로
   검증하고, 내부 review 경로에만 노출한다. 현재 이 증인 전용 parser/import/API는 미구현이다.
3. **기관·인물 연결:** 맥의 정확한 DB에서 기관을 검토하고 source row별로 Person 신원을 해결한다.
   원문 소속과 대상기관을 별개 관계로 유지한다. 기존 staging UUID, 이름 일치, 기관 근접성은
   승인 근거가 아니다. 신원이 미해결이면 source-scoped 후보를 유지한다.
4. **공개 근거 및 화면:** 기존 Claim/Evidence 공개 검증을 통과한 결과만 기존 국감 화면에 붙인다.
   기관 아래 세 범주의 출석요구 인물·소속·일시와 출처를 보여주고 인물 상세와 연결한다.
   `출석요구 명단 기재`와 `실제 출석`은 별도 상태와 근거다. ALIO의 source-listed node 모양을
   참고할 수 있지만 ALIO 역할/Person materializer 또는 `APPEARED_AT`를 증인 명단에 적용하지 않는다.
5. **SSD·사이트 검증:** 같은 맥 SSD API를 사용해 읽기/증거 경로와 빈값·장애·미해결 신원을
   검증한 뒤 Aside 데스크톱·모바일 검증, Workers/Sites 연결을 진행한다. 데이터 계약이 준비되면
   Opus에는 기존 DESIGN을 유지한 기관·출석요구 인물 UI만 맡기고 Codex가 게이트와 통합을 검증한다.

이 연구 산출물에서 운영 데이터·Person·Organization·identity link·Claim·Evidence 생성은 모두 0이다.
기존 사이트가 새 명단을 표시하는 상태는 아직 아니다.
